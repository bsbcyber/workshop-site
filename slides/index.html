04

I’m here to get you a live resume URL.

Not a toy demo — your content, a real pull request with a partner review, and GitHub Pages publishing the way teams actually ship. Ask questions early. Stuck is normal; guessing burns time.

05

Today’s job: make this site yours, then publish it.

Name, education, coursework, projects, photo if you want — then a real GitHub Pages URL. We’ll use a branch and pull request so you practice how teams review work before it goes live.

06

First: download and unzip.

You want a folder named my-resume-site. Also create an empty Public GitHub repo — leave README / .gitignore / license unchecked.

portfolio-starter.zip ↓

Inside the folder there’s a WORKSHOP.md you can follow in VS Code if you prefer checkboxes over this screen.

07

Open the folder in VS Code and run it.

npm install
npm run dev

Click the localhost link in the terminal. You should see a sample resume. Leave that terminal running.

08

Almost everything you edit is one file.

src → data → profile.js

Name, about, coursework, projects, links. Optional photo: drop photo.jpg in public/. Leave lists you don’t need as [].

09

Saving a file does not put it on the internet.

save → commit → push / PR → deploy

We’ll hit each of those on purpose. Don’t skip ahead.

10

Push the starter to your empty repo.

git init
git add .
git commit -m "Create my portfolio"
git branch -M main
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
git push -u origin main

If Actions shows a red X after this: that’s normal for now. We turn Pages on later and re-run.

11

When something looks wrong, run git status first.

Then git diff if you need to see what you edited. Guessing burns time.

12

Build out your resume in profile.js.

Replace the sample person with you. Fill what you have — coursework, activities, projects, experience if any. Replace every example.com link. Save and check localhost. Don’t Commit yet; next we ship a chunk of this work through a pull request.

13

Pick one piece of that resume work for a pull request.

Example: featured project card. GitHub → Issues → New. Write how you’ll know it’s done — honest summary, working link, readable on a phone, no secrets. The rest of your personalization can ride in the same commit.

14

Status Bar: click main, then create a branch.

Name it add-featured-project. The Status Bar should show that name before you commit anything.

15

Now commit — on that branch.

Source Control → read the diff → Stage (+) → write a real message → Commit → Publish Branch.

“updates” is not a message. “Add featured project card” is.

16

Open the PR. Attach it to your issue.

Issue = task. PR = fix. Two ways: (1) put Closes #1 on its own line in the PR body — closes the issue on merge. (2) PR sidebar → Development → Link an issue → pick yours. Confirm the link on the issue page, then Files changed. Don’t merge yet.

17

Hand your PR to the person beside you for a +1.

They open Files changed, skim the diff, then Review changes → Approve (or Comment with +1). You do the same on theirs. Merge only after you have a partner review.

18

Your ZIP already includes a GitHub Actions workflow.

.github → workflows → deploy.yml

On a push to main it installs, builds, and deploys. You’re not writing YAML today — you’re watching it run. Feature branches don’t publish.

19

Turn Pages on, then re-run the failed job.

Settings → Pages → Source: GitHub Actions. Actions tab → open the run → Re-run all jobs if it failed earlier. When it’s green, open the URL and poke it on your phone.

20

Lab: finish your resume content, then ship it.

Keep filling profile.js. Use the issue → branch → PR → partner +1 path for the featured project. Then Pages → live URL. Stuck? Show the error and your Status Bar branch name.

21

Show a partner your live resume — and the PR that got it there.

If the site still looks like Jordan Lee, you’re not done yet.
